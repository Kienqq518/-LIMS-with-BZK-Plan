# LIMS 集成 AI 报告审核 · 系统设计架构（多行业可扩展）

> 定位：把 AI 报告审核做成**我们 LIMS 产品的内生能力**，而非独立 SaaS 审查器。  
> MVP：以**电网检测**（电网物资 / 安全工器具 / 电缆等）为试点闭环；化学、汽车零部件等行业通过「行业包」迭代接入。  
> 基准：在现有 M1 设计（`docs/superpowers/specs/2026-11-11-lims-ai-review-m1-design.md`）之上补齐**多行业扩展轴**；借鉴 IACheck 的方法论，但不照搬其「独立质控中台」形态。  
> 整理时间：2026-11-13。

---

## 0. 一句话结论

**核心骨架用「LIMS 内嵌编排 + 双引擎（规则优先 / LLM 补位）+ 四级级审核范围 + 行业包插件」；MVP 只跑电网的 L1/L2（形式 + 内部逻辑）确定性规则闭环，把「行业 / 品类 / 标准库 / 案例回流」做成可热插拔结构，化学与汽车零部件后续只加包、不改地基。**

---

## 1. 我们与 IACheck 的定位差（决定架构取舍）

| 维度 | IACheck | 我们 |
|---|---|---|
| 产品形态 | 独立 AI 审核助手 / 可嵌入 LIMS·OA 的中台能力 | **LIMS 主营产品上的增值能力**，审核嵌在「编制→审核→签发」链路里 |
| 客户 | 泛 TIC | 国网 / 电科院 / 第三方电力检测 / 电缆厂；今年扩化学、汽车零部件 |
| 数据优势 | 偏文档 OCR + 外挂标准库 | **原生握有委托、样品、原始记录、设备、标准、人员资质**——这是最大护城河 |
| MVP 策略 | 广行业通用产品 | **先电网深闭环，再按行业包横向复制** |
| 责任边界 | 强调 AI 预审 + 人工 | **必须更硬**：AI 永不自动签发；严重项可建议退回，最终责任在授权签字人 |

**因此：不抄 IACheck 的「接入层做多端 SaaS」；重点抄它的「四级范围 + 规则/大模型双引擎 + 置信度人机分工 + 案例回池」。我们的差异化是「审核能打到 LIMS 结构化数据与溯源」，而不是「更好的 OCR」。**

## 2. 设计原则（约束后续一切选型）

1. **嵌入流程，不另起系统**：审核结果出现在报告审核节点与统一工作台；不强迫用户离开 LIMS。
2. **行业可插拔（Industry Pack）**：通用引擎固定；行业差异进「规则包 / 标准包 / 模板映射 / 术语」，禁止把化学限值写进电网硬编码。
3. **规则优先，模型补位**：确定性规则保可控、可解释、可飞检举证；LLM/ML 只处理语义与模糊项，且默认进「需复核」。
4. **四级范围 = 实施路线图**：L1→L4 既是能力分级，也是分期交付边界（见 §5）。
5. **AI 预审、人终审**：结论三态（通过 / 需复核 / 不通过建议）；人工覆盖必留痕；案例回池服务下一期模型。
6. **只读业务、自写审核域**：AI 服务不回写委托/样品主数据；只写 `ai_review_*`；退回动作走 LIMS 既有流程 API（由编排器调 LIMS，而非引擎直接改库）。
7. **配置变更可控**：规则 / 行业包上下线走版本 + 审批 + 灰度（领域/客户），满足检测机构合规习惯。

## 3. 目标架构总览

细粒度交互图（推荐）：

- 源文件：[`docs/feishu/LIMS-AI-Review-系统架构总览.excalidraw`](../feishu/LIMS-AI-Review-系统架构总览.excalidraw)
- 在线打开：[Excalidraw 分享链接](https://excalidraw.com/#json=dSenQQGSK-tvu4JCEv1xs,qaUhooln98KYXCjI_G17Qw)

分层要点：① 用户交互层（嵌入现有 LIMS）→ ② Orchestrator（鉴权/PackResolver/调度/三态聚合）→ ③a 引擎 · ③b LIMS数据层 · ③c 行业包 → ④ 审核数据域（自写、不回写 LIMS 主数据）。  
**布局说明**：主栏通栏 **1 → 2 → 3a → 4**；右侧 **3b LIMS数据层 / 3c 知识组装**。每层一色（靛蓝 / 琥珀 / 绿 / 深蓝 / 青）；**只画层间箭头**（层内模块用文案标明顺序，不互挂箭头）。3c 的「品类绑定 + 标准/限值库」包在 **Industry Pack** 模块内。

**层间交互（图上仅这些箭头）**：1→2 触发；2→3a 调度执行；3a→4 落库；4→2 反馈（虚线）；3b→3a 取数；3c→3a 依据；3c→2 装载规则集（虚线）。层内顺序用标题文案表达，不画模块间箭头。

**第 3 层 vs 第 4 层：**
- **第 4 层 = AI 审核自有库**（`ai_review_*` 表），不是 LIMS 业务库；LIMS 主数据只读、不回写。
- **配置域**（行业包 / 包产物 / 品类 / 绑定 / 规则）：配置主数据，由规则台账维护；**供 3c / PackResolver 读取**以组装「本次规则集」。其中 **包产物** = 行业包内的版本化内容（标准表、术语、模板映射等），挂在 `industry_packs` 下。
- **运行域**（results / issues / feedback / cases）：**每次 AI 审核完成后的留档**（3a/编排器写入）；案例库为学习旁路。不要把「审核留档」理解成配置域。


**3a 读法**：左「主引擎 MVP（RuleEngine）」· 右「补位可选（LLM/ML/网关，虚线框）」· 底「共用出口（门控→三态结论）」。不是一排平级盒子。

**3c 内部关系（固定组装，不是平级堆叠）：**

```
① 通用规则集（跨行业底座）
        ↓ 叠加
② Industry Pack（按 industry_code 加载的行业插件）
        ├── 品类绑定 / param_schema（按品类覆盖参数与规则）
        └── 标准 / 限值库（现行有效、合格上下限；服务 L3）
        ↓ 产出
③ 本次规则集 ──→ PackResolver / 引擎

旁路：案例回池 ← 人工反馈（误报/漏报/正常）；用于学习与后续优化，不进入当次判定主路径
```


## 4. 关键扩展轴：行业包（Industry Pack）

多行业扩展的主轴不是「再写一个引擎」，而是：

```
Industry Pack = {
  industry_code,          # power_grid | chemical | auto_parts | …
  name, version,
  category_bindings[],    # 品类 ↔ 规则（可覆盖 param_schema）
  rule_overrides[],       # 启用/停用/改严重度/改参数（相对通用集）
  standard_refs[],        # 本行业标准号、限值表、有效期策略
  template_profiles[],    # 报告模板字段映射（结构化取数契约）
  term_dict[],            # 术语与同义词（供后期 LLM）
  policy: {
    auto_return_on_severe,   # 是否允许「严重 → 自动建议退回」
    confidence_threshold,    # 如 90；低于则强制需复核
    enabled_levels: [L1,L2]  # MVP 电网只开 L1/L2
  }
}
```

**运行时解析顺序（必须固定，避免行业串味）：**

1. 加载**通用规则集**（跨行业成立，如日期链、签名位、标准号带年号）  
2. 按报告的 `industry_code` 加载行业包  
3. 按 `category_code`（品类）叠加绑定与 `param_schema` 覆盖  
4. 产出「本次规则集 + 参数 + 启用级别」交给引擎  
5. 未识别行业 / 品类 → 只跑通用集 + 提示码（对齐现有 `CAT-UNCAT-01` 思路，可扩展 `IND-UNCAT-01`）

**禁止事项：** 在 RuleEngine 里写 `if (电缆) … else if (试剂) …`；行业差异必须进包配置。

## 5. 四级审核范围 × 分期（借鉴 IACheck，落到我们节奏）

| 级别 | 审什么 | 主要依赖 | MVP 电网 | 化学 / 汽车零部件 |
|---|---|---|---|---|
| **L1 基础形式** | 编号、签名、章节/字段齐全、单位、格式 | 报告结构 + 模板映射 | **必做** | 复用通用 + 换模板映射 |
| **L2 数据逻辑** | 日期链、委托项↔结果、设备校准覆盖、内部勾稽 | LIMS 结构化数据 | **必做** | 复用通用逻辑；行业特有勾稽进包 |
| **L3 合规对齐** | 标准现行有效、限值符合、方法/项目完整性 | 标准库 / 限值表 / 方法库 | **试点 1～2 条**（如标准年号、引用=实测标准） | 随行业包建设标准库后加重 |
| **L4 溯源验证** | 原始记录哈希/时间戳、人员资质、CMA 范围、透明度溯源码 | 设备/资质/溯源模块 | **预留接口**，不进 MVP 闭环 | 与「报告透明度 / 溯源码」能力联动后开 |

MVP 成功标准：**电网 L1+L2 闭环可上线给电科院/第三方试点客户用**；L3 浅做、L4 占位。这与 IACheck「先易后难、先内后外」一致，但我们把 L2 优势建立在 LIMS 结构化数据上，而不是 OCR。

## 6. 引擎设计：规则主引擎 + 模型辅引擎

### 6.1 RuleEngine（MVP 主路径）

- 输入：结构化报告快照（由集成层按模板映射组装的 canonical JSON）  
- 执行：确定性谓词；每条产出 `pass/hit + severity + evidence`  
- 聚合（沿用 M1，可配置）：  
  - 任一「严重」→ **不通过（建议退回）**  
  - 无严重、有「一般」→ **需复核**  
  - 其余 → **通过（可含提示）**  
- 输出必须可解释：规则 ID、命中字段、证据快照——服务飞检与客户信任。

### 6.2 LLM / Agent（二期补位，架构先留）

适用：术语规范、结论与数据是否自洽、跨段矛盾、非结构化附件说明等。  
约束：

- 默认 `confidence < threshold` → 降级为「需复核」，禁止单独触发自动退回  
- 强制结构化输出（问题列表 schema），禁止自由改写报告正文  
- 超长报告用「按检测项目/章节分块 + 跨块一致性汇总」（Map-Reduce），与 IACheck 同构但我们优先切 LIMS 已有项目结构，而非纯 OCR 切片

### 6.3 置信度与人机门控

```
Rule 命中严重     → 不通过建议（可配置是否自动退回编制）
Rule 命中一般     → 需复核
LLM 低置信 / 冲突 → 需复核
人工覆盖          → 必填理由 → feedback + cases（误报/漏报/正常）
```

## 7. 与 LIMS 的集成契约

### 7.1 触发

- **主路径**：流程进入「报告审核」时 LIMS 发领域事件 / 回调 Orchestrator  
- **降级**：无事件能力时 Orchestrator 轮询只读状态  
- **幂等键**：`report_id + report_revision`（同版本不重复计费式狂跑）

### 7.2 取数（Canonical Report Snapshot）

统一快照字段（行业无关的核心集）示例：

| 分组 | 字段示例 |
|---|---|
| 身份 | report_id, industry_code, category_code, business_type（型式/出厂/委托/抽样…） |
| 日期 | receive_date, test_date, report_date（抽样日期仅抽样类业务可选） |
| 项目结果 | entrust_items[], result_params[], values[], units[] |
| 标准 | test_standard, cited_standard |
| 设备人员 | devices[].calib_from/to, signatures{tester,reviewer,approver} |
| 扩展 | `ext`（行业包自定义，化学浓度/汽车扭矩等放这里） |

行业特有字段进 `ext` + 模板映射，**不污染核心 schema**。

### 7.3 回写边界

| 允许 | 禁止 |
|---|---|
| 写 `ai_review_*` | 直接改委托/样品/原始记录 |
| 调 LIMS「退回编制 / 待审核」流程 API（编排器） | 引擎私自改报告状态 |
| 写案例库标注 | AI 自动签发 / 自动生成合格证 |

这与当前原型「严重不通过可自动回退编制、标注仅用于学习」一致，目标系统用正式流程 API 固化。

## 8. 数据模型（在 M1 七表上的增量）

保留 M1：`rules / results / issues / feedback / cases / categories / bindings`。关系见架构总览图第 4 层：

```
配置域：industry_packs ─1:N→ pack_artifacts
        industry_packs ─scope→ rules
        categories ─1:N→ bindings ─N:1→ rules

运行域：results ─1:N→ issues ─(rule_id)→ rules
        issues ─→ feedback ─→ cases（学习旁路）
```

**新增 / 强化：**

| 对象 | 用途 |
|---|---|
| `ai_review_industry_packs` | 行业包元数据与版本、启用级别、策略 |
| `ai_review_pack_artifacts` | 包内标准表、术语、模板映射的版本化产物 |
| `rules.industry_scope` | `universal` / `pack:<code>`；与 `is_universal` 兼容演进 |
| `cases.industry_code` | 案例按行业分桶，供后续分行业微调 |

规则变更控制字段继续沿用：`version / effective_from / effective_to / approved_by / change_ticket`。

## 9. MVP（电网试点）范围切片

### 9.1 In Scope

- 行业包：`power_grid`（电网物资 + 安全工器具；电缆可作为同包下品类）  
- 引擎：仅 RuleEngine；8+ 条通用规则（现有 M1）+ 少量电网品类绑定（有限值才上）  
- 级别：L1 + L2 全开；L3 仅已有确定性项（标准年号、引用一致性）  
- 入口：报告审核详情内嵌结论区 + AI 审核工作台  
- 闭环：自动触发 → 三态结论 → 人工处置/建议退回 → cases 沉淀  
- 部署：目标独立微服务（FastAPI 等）只读接 LIMS；原型仓继续先行验证交互

### 9.2 Out of Scope（明确不做，避免摊大饼）

- 化学 / 汽车零部件规则与标准库建设  
- OCR 扫描件主路径（我们以 LIMS 结构化数据为主；附件 OCR 可三期）  
- Agent 蜂群调度、Skill 可视化编排（可列为远期，不挡 MVP）  
- AI 自动签发、无留痕覆盖  
- L4 全量溯源（只留接口与字段）

### 9.3 MVP 验收（产品口径）

1. 电网试点客户的典型报告（型式 / 出厂 / 委托 / 抽样）进入审核即出 AI 结论  
2. 严重项可走「建议退回编制」，人工可覆盖并留痕  
3. 换一份「未配置品类」报告只跑通用集，不出现化学/汽车误杀  
4. 规则台账可按行业包过滤；新增一条电网品类规则**无需改引擎代码**（只改配置/包）  
5. 案例库按行业写入，具备后续训练字段

## 10. 后续行业扩展套路（化学 / 汽车零部件）

对每个新行业，固定流水线（复制电网包，不改 Orchestrator）：

1. **盘点**：报告模板、必填字段、高频退回原因、适用标准清单  
2. **映射**：做 `template_profile` → canonical snapshot（`ext` 承载特有量）  
3. **规则**：先搬运通用集；再加行业 L2/L3（限值、方法、平行样等）  
4. **绑定**：品类 × 规则 + `param_schema`（浓度限、扭矩公差等）  
5. **灰度**：单客户 / 单品类开启 → 误报率达标 → 全量  
6. **回流**：该行业 cases 单独评估，再考虑行业 LLM 提示词或小模型

**扩展成本应落在「配包」而不是「改平台」。** 若某需求必须改 Orchestrator / 核心 schema，需升级平台版本并评审。

## 11. 逻辑部署与安全

```
[LIMS 主系统] ←只读/事件→ [AI Review 服务] ←→ [规则/行业包/案例库]
        ↑                         │
   同客户私有化 / 专有云            └─ 可选：内网 LLM 网关
```

- 国网 / 电科院场景默认**私有化或客户专有云**，数据不出域  
- 审计：每次审查的规则版本、包版本、输入快照哈希、结论、人工处置全留痕  
- 权限：规则配置与审核处置分角色；双人复核策略可由行业包 `policy` 打开

| 已有 | 本架构中的位置 |
|---|---|
| M1 Spec / 8 条通用规则 / 三态聚合 | MVP RuleEngine 与结论策略的直接实现基线 |
| `ai-review-engine.js` / `ai-review-store.js` | 原型验证床；表结构向目标库迁移 |
| 通用/品类绑定设计 | 升级为「通用 → 行业包 → 品类」三层 |
| 报告审核两页 + 自动退回 | LIMS 嵌入式交互的产品形态保持 |
| 报告透明度 / 溯源码 | L4 远期对接点，不进 MVP |
| IACheck 分析报告 | 方法论来源；本架构已做「嵌入 LIMS + 行业包」改造 |

---

## 13. 分期路线（建议）

| 阶段 | 主题 | 交付 |
|---|---|---|
| **M1 / MVP** | 电网 L1+L2 闭环 | 通用规则 + `power_grid` 包骨架 + 审核嵌入 + 案例只写 |
| **M2** | 电网加深 | 品类绑定实装、电网限值/平行样等 L2/L3、规则变更控制上线 |
| **M3** | 平台硬化 | 真实微服务、事件触发、包热更新、多租户/私有化交付件 |
| **M4** | 第二行业 | 化学或汽车零部件择一打穿（完整行业包） |
| **M5** | 智能补位 | LLM 语义项 + 置信度门控 + 案例消费（分行业评估） |
| **M6** | L4 溯源 | 原始数据/资质/透明度联动 |

---

## 14. 风险与对策

| 风险 | 对策 |
|---|---|
| 把行业 if-else 写进引擎 | Code Review 红线 + 行业包强制；CI 检查无硬编码行业名 |
| 标准库维护跟不上 | L3 缓开；先做「标准号有效性 / 引用一致」等低成本项 |
| 客户要「AI 直接签发」 | 产品红线：永不默认开启；合同与界面明示责任人 |
| 字段因模板而异 | 模板映射层 + 缺字段降级为 A 类完整性，不硬报逻辑错 |
| 多行业案例污染训练 | `cases.industry_code` 分桶；微调按包隔离 |

---

## 15. 决策清单（供拍板）

1. **产品形态**：确认「LIMS 内嵌能力」而非独立审核 SaaS。  
2. **扩展轴**：确认「行业包」为唯一横向扩展方式。  
3. **MVP 级别**：确认电网只承诺 L1+L2（+少量 L3 确定性项）。  
4. **责任**：确认 AI 不自动签发；严重项退回策略按行业包可配。  
5. **下一行业**：M4 优先化学还是汽车零部件——不影响本架构，但影响标准库投入顺序。

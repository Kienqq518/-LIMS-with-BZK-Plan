# 标准文件库 与 任务发现 设计 v0.1

> 解决两件事：**标准文件不再被重复上传、重复拆解**；**一份能力表覆盖多标准时怎么切成任务**。
> 上层流程见 `docs/ai-workbench-page-design-v0.1.md`，数据接口见 `docs/standard-library-excel-contract-v0.2.md`。

---

## 一、为什么必须单独做这一块

上线时会预存一批已有标准文件。此后客户每传一份，都要**永久存档**。
不做这层，10 个客户做同一个 GB/T 12706.2 就要上传 10 次、OCR 10 次、拆解 10 次、专家校稿 10 次——
AI 帮的忙会被重复劳动吃干净。做了这层，**第 2 个客户开始就是白捡**：
元数据现成、代替关系现成、最关键是**拆解成果现成**。

所以这个库的价值排序是：**拆解成果 > 元数据 > 文件本体**。文件那几 MB 不是复利来源。

---

## 二、三层结构

| 层 | 内容 | 共享性 | 说明 |
|---|---|---|---|
| L1 元数据 | 规范化编号、标准名称、年号、状态（现行/被代替/废止）、代替关系、发布/实施日期、层级角色 | **全局共享** | 所有人都能看到"这个标准存在、什么状态、被拆成什么样" |
| L2 文件本体 | PDF 原件 + 内容 hash + 页数 + 文本层质量评分 | **按客户隔离** | 只有上传者能看到原文；别人命中时看到的是"库里已有该标准，请上传你的副本 / 申请获取" |
| L3 拆解成果 | 定稿稿件（Excel 配置包）+ 结构化入库数据 + 校稿问答记录 | 全局共享（内部档回流）；客户档只进本环境 | 复利本体。同一标准第二次拆解时优先复用 |

**为什么这么切**：私有化部署本来就没法共享；云部署技术上能全共享，但把 PDF 原件跨客户可见有合规风险。
去重收益的大头来自 L1 + L3，摘掉 L2 的共享几乎不损失什么，却把风险摘干净了。

部署差异：

| 部署 | L1 | L2 | L3 |
|---|---|---|---|
| 云（SaaS） | 全局 | 按客户隔离（可选申请） | 内部档回流全局；客户档隔离 |
| 私有化 | 单租户内全局 | 单租户内全局 | 单租户内全局 |

## 三、标准文件的身份键：规范化编号 + 名称，从正文识别

判定"是不是同一份文件"的唯一依据是**文件实体里真正的编号和名称**，不是用户给文件起的名字，
也不能靠正则从文件名里猜。理由：编号里天然存在 `-` `/` `:` 和不同排版（`GB/T 12706.2-2020`、
`DL/T 802.3—2023`（全角破折号）、`EN 50306-2:2020`、`IEC 61156-5 (2020)`），文件名更是千奇百怪。

### 3.1 识别流程

1. 取 PDF 前 3 页 + 页眉页脚 + 封面文本层（扫描件先 OCR 并记录置信度）。
2. 抽取候选编号串，做**规范化**：
   - 全角符号归一半角（`—`→`-`，`（）`→`()`，全角数字/字母→半角）
   - 去空格与连接符差异（`GB/T` / `GB／T` / `GB T` → `GB/T`）
   - 拆出 `机构前缀 + 序号 + 年号`：`GB/T 12706.2-2020` → 前缀 `GB/T`、序号 `12706.2`、年号 `2020`
   - 没有年号的（部分 EN/IEC 封面把年号放出版信息里）→ 从出版行/版权行取，取不到则年号留空并降级为"待人工确认"
3. 规范化键 = `前缀 + 序号 + 年号`；标准名称做二次校验（去空格、去标点、大小写归一后比对）。
4. **编号一致且名称一致 ⇒ 同一份文件**。名称不一致 ⇒ 不自动合并，走人工确认（可能是翻译差异，也可能是不同部分被写错序号）。
5. 内容 hash 相同 ⇒ 直接判定同一份，跳过以上全部（最快路径，也是"同一文件重复上传"的兜底）。

### 3.2 失败降级

| 情况 | 行为 |
|---|---|
| 正文里抽不到编号 | 不猜。弹范围级问题让人填编号+名称，AI 把候选列出来供选 |
| 抽出多个编号（合集/丛书） | 走任务发现（第五节），一份文件可能对应多个任务 |
| OCR 置信度低 | 标记"文本层不可靠"，该文件的 L3 成果可复用，但重新拆解时提示需清晰版 |

### 3.3 状态与代替关系

- 状态只有三种：`现行` / `被代替` / `废止`。
- 存 `代替` 与 `被代替` 双向边，形成链：`GB/T 12706.2-2008 ←被代替← GB/T 12706.2-2020`。
- **废止标准照样能被选中做检测依据**，不做任何限制。原因：样品按旧标准生产，检测时标准已更新但不能按新标准测。
  界面只在选中废止标准时给一条**非阻断**提示（"该标准已废止，请确认检测依据确为旧版"），记录确认人。

## 四、库的管理页面（AI 助手模块下，与工作台平级）

```
+--------------------------------------------------------------------------+
| 标准文件库   [搜索: 编号/名称/关键词]  [状态▾] [机构▾] [已拆解▾]  [上传] │
+----------------+---------------------------------------------------------+
| 左：结果列表   | 右：详情三栏 Tab                                         |
|  编号  年号 状态|   元数据 | 文件本体 | 拆解成果 | 引用与复用 | 变更记录  |
|  名称        |                                                          |
|  拆解状态徽标 |                                                          |
+----------------+---------------------------------------------------------+
```

- **列表行**：规范化编号（等宽字体）、名称、状态徽标、年号、是否已拆解（有几个版本）、被引用次数。
- **元数据 Tab**：可编辑的字段仅名称/别名/备注；编号与年号来自识别结果，改动要留痕并触发"重新比对"。
  代替关系在这里以时间线呈现。
- **文件本体 Tab**：只显示**本客户可见**的副本；他人上传的显示"库里已有，请上传你的副本 / 申请获取"。
  展示 hash、页数、文本层质量分。
- **拆解成果 Tab**（价值最高）：列出该标准已定稿的稿件版本、覆盖的样品/型号/试验项数量、
  校稿时问答过的范围级问题（下次直接跳过）、最近一次入库时间。
  操作：`以此拆解新任务`（复用）、`对比两个稿件版本`、`下载稿件`。
- **引用与复用 Tab**：哪些客户/任务用了这份标准、复用了哪一版成果 —— 这是"复利"的可视化，也是内部档的运营看板。
- **变更记录**：谁上传、谁改了元数据、谁定稿了哪版成果。

## 五、任务发现：一份能力表 → N 个任务

### 5.1 层级角色（先分类，再切任务）

| 角色 | 定义 | 例子 | 对分类树的影响 |
|---|---|---|---|
| 总标准（集合型） | 说明"这一类东西有哪些类型"，各类型指向各自子标准 | DL/T 802.1—2023 讲电缆保护管有哪些类型 | 挂在**大类样品分类**节点上（电缆保护管），本身不直接产生样品数据任务 |
| 子标准 | 总标准点名的某一类型的详细技术要求 | DL/T 802.3—2023 实壁类 | 挂在**下层样品分类**节点（实壁类塑料电缆导管）下 |
| 独立标准 | 不属于任何总标准，自己就是一类样品 | GB/T 12706.2 | 直接挂在对应样品分类下 |

同一分类节点下可以并列多个**同编号不同年号**的标准文件节点（版本随年代更新时新增，不覆盖旧的）。
若某类型没有独立子标准，则不需要子标准节点 —— 层级是**推导出来的，不是写死的**。

### 5.2 算法（AI 先给清单，人确认后才开工）

```
输入：能力范围表 PDF（+ 已上传的标准文件 + 库内元数据）
1. 从能力表抽出「检测对象 / 样品大类 / 型号 / 试验项 / 量程 / 说明列限制」
2. 每个检测对象 → 匹配检测依据标准 → 规范化编号
3. 对每个编号取库内元数据：
   - 是总标准？→ 查它点名了哪些子标准 → 与能力表实际覆盖的类型求交集
     → 交集里每个子标准 = 一个任务；能力表提到但库里没有文件的 → 列入"需补文件"
   - 是子标准/独立标准 → 1 个任务
4. 合并同编号的任务（不同样品同一标准 = 同一任务内的多个样品分块）
5. 输出任务清单预览表 → 人确认/增删 → 落 00_包信息.任务列表
```

关键口径（都是之前拍过的，这里固化）：

- 只上传了总标准（802.1）却判断出各类型有各自子标准 ⇒ **告知需按子标准各拆一任务、预计 N 个**，
  缺文件让客户传；生成的任务一定落在能力范围表之内，不凭空扩样。
- 标准文件里明确提到其他型号，但报告/记录单没提 ⇒ 问"是否一并拆解 型号 xxx/xxx"，以人答为准。
- 标准文件里有型号列举 ⇒ `区分型号=是`；没有 ⇒ `=否`。
- 能力表"说明"列的限制（只测 0.1μΩ~300Ω、只测 ≤120mm² 的绝缘电阻、只测 0~40kV 交流高压）
  ⇒ 会砍掉部分型号/样品分类，**砍哪些由 AI 推断，但推断结果一律进范围级问题问人**，不静默砍。
- 报告模板里抄来的值（如 `≤20.0 Ω/km`）**不自动算已验证**，必须回到检测依据标准文件里验证；
  验证不到 ⇒ 置信度 `未验证` 并提问。标准文件才是权威。

### 5.3 复用命中时的询问（必须问，不能替人决定）

```
库里已有 GB/T 12706.2-2020，拆解成果 v3-final（覆盖 6 个样品 / 41 个试验项，2026-10-12 定稿）
你上传的是同一份文件（内容 hash 一致）。本次怎么拆？
  A. 按库内成果拆（推荐：直接复用，只需补你们实验室的量程与型号裁剪）
  B. 按你上传的这份重新拆（慢，产出只进你们环境）
  C. 以库内成果为底，逐条对比你这份后合并差异（折中，会列出差异让你确认）
```

选 A/C 时，能力表的裁剪逻辑（量程、说明列）仍然照客户实际情况重算 —— 复用**标准侧的骨架**，不复用**客户侧的能力**。

## 六、数据模型草案

```
std_file          (id, norm_code, prefix, serial, year, title, title_alt[], status,
                   supersedes[], superseded_by[], role, publish_date, effect_date,
                   created_by, created_at, meta_locked)
std_file_blob     (id, std_id, tenant_id, sha256, page_count, text_quality,
                   source, uploaded_at, visible_to_owner_only)
std_derivation    (id, std_id, task_key, draft_version, status, sample_count,
                   test_item_count, param_count, finalized_by, finalized_at,
                   scope_qa_json, tenant_scope)          -- L3 拆解成果
std_derivation_ref(id, derivation_id, ref_tenant, ref_task, used_at)  -- 复用统计
std_task          (id, pkg_id, std_id, role, scope_note, status, created_at)
std_upload_issue  (id, blob_id, kind, detail, resolved_by, resolved_at) -- 识别失败台账
```

`norm_code` 上有唯一约束（`prefix + serial + year`），`title` 参与二次校验但不进唯一键。

## 七、边界与风险

| 风险 | 处置 |
|---|---|
| 客户上传的"同一标准"其实是删减版/翻译版 | hash 不同 + 编号相同 ⇒ 不合并文件本体，只共享元数据；成果复用时提示"你的副本与库内版本内容不一致，建议选 C 逐条对比" |
| 编号识别错（把部分号当序号，如 12706.2 vs 12706） | 名称做二次校验；两者都存 `候选编号`，冲突时人工确认，不自动落库 |
| 总标准与子标准关系识别不全 | 关系来自正文引用（"参见 DL/T 802.3"），抽不到就问人；关系可人工维护并留痕 |
| 废止标准被误限制选择 | 明确不做限制，只提示（业务上真实存在按旧标准检测） |
| 跨客户看原文的合规风险 | L2 默认隔离；申请获取走人工审批，留审计 |
| 库内成果被别人改坏 | 定稿稿件不可变；改动 = 新版本；引用方显示所引用的具体版本号 |

## 八、落地顺序

1. L1 元数据 + 规范化识别 + 代替关系（先能去重）
2. L2 存档 + hash + 隔离策略（先只存不共享）
3. L3 成果表 + 命中询问（A/B/C 三选）+ 复用统计（复利开始）
4. 任务发现算法 + 任务清单预览表（跟工作台 F1 一起做）
5. 管理页面四 Tab + 引用看板（内部档运营用）

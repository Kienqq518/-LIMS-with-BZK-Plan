## 0. 已确认决策一览

### 0.1 首轮（Q1–Q8）

| 议题 | 决策 |
|------|------|
| Q1 系统 vs 人工 | 系统回填权威 → 新主版本并 current；仅最新版可编 |
| Q2 签字/审核 | 原始记录落款角色可配；核校取数据审核人（常 1 人）；报告可双人审核 |
| Q3 流转单 | 仅内容回填节点打主版本 |
| Q4 预通知书 | 非文件；「查看更多」只读预览 |
| Q5 版本号 | `V{major}.{minor}`；列表无后缀；「查看历史」权限控制 |
| Q6 编辑 | PageOffice；会话内保存不落版，关闭落次版本 |
| Q7 回滚 | 仅同 major 次版本；再生成一版 |
| Q8 多格式 | 同一 version 挂 Word + PDF |

### 0.2 次轮（F1–F5）

| 议题 | 决策 |
|------|------|
| F1 旧主版本 | **按角色数据权限**：业务人员只看**当前最新主版本**下的全部次版本；质量负责人等高级角色可看**旧主版本历史** |
| F1 流程回退 | 流程从下一节点**回退到上一节点**也会引起**主版本变动**（同属 SYSTEM 权威更新） |
| F2 历史是否含 `V{n}.0` | **展示**；可见范围遵循 F1 |
| F3 回滚记法 | **A+B**：新建次版本（如 V2.3）+ 字段「回滚自 Vx.y」 |
| F4 变更原因 | **本期不记录** |
| F5 签发后编辑 | **系统配置项**；「谁能改这项配置」本身也要权限控制 |

### 0.3 延伸：合规版 / 实务版一键切换（骨架，细节后续补）

已记录两点设想并展开为 §10 方案：

1. **报告签发后是否允许在线编辑**：实务版下可配置；合规版下隐藏配置且强制禁止（除非走退回）  
2. **查看历史弹窗**：合规版下只展示系统更新的主版本，次版本不在页面展示

## 1. 背景与目标

两类文件更新：

1. **SYSTEM**：流程节点通过（或流程回退）后回填文件对应位置（权威）→ 升 **major**  
2. **MANUAL**：PageOffice 编辑并关闭 → 升 **minor**

目标：业务可用性与 17025 检查要求可切换；版本、权限、历史可见性分层清晰。

## 3. 版本号语义

### 3.1 格式

`V{major}.{minor}`（如 `V1.0`、`V2.1`）。

| 事件 | 变化 | source |
|------|------|--------|
| 首次生成 | `V1.0` | SYSTEM |
| 节点通过且内容变化 | `V{n}.0` → `V{n+1}.0` | SYSTEM |
| **流程回退**且文件内容需按回退后状态重写 | `V{n}.0` → `V{n+1}.0` | SYSTEM（`origin=workflow_rollback`） |
| PageOffice 保存并关闭 | `V{n}.{m}` → `V{n}.{m+1}` | MANUAL |
| 文件次版本回滚（同 major） | 新建 `V{n}.{m+1}`，内容=目标版 | MANUAL + `rollbackFromVersionId` |

无内容变化 → 不打版。列表文件名**不带**版本后缀。

### 3.2 流程回退与主版本

流程存在「下一节点 → 回退上一节点」：

- 回退若导致文件对应位置内容变更（清除/改写节点回填区）→ **必须**升 major，新 `V{n+1}.0` 为 current  
- 与节点前进回填同一套 SYSTEM 规则：权威、业务默认看不到被取代的旧主版  
- 审计日志记录：`triggerEvent=WORKFLOW_ROLLBACK`、自节点、至节点、操作人  

> 主版本号表示「系统权威内容世代」，**不表示流程前进方向**；前进与回退只要改了文件，都升 major。

### 3.3 次版本回滚（文件内容回滚，非流程回退）

- 仅同 major：`V2.2` → 可回滚到 `V2.1` / `V2.0`，不可到 `V1.x`  
- 生成新次版本（例 `V2.3`），来源展示「回滚」，并写 `rollbackFromVersionId` / 文案「回滚自 V2.1」  
- 不删中间历史  

### 3.4 PageOffice

- 打开前：保证 current 已是正式版（基线）  
- 会话内多次保存 → **不**建 `DocumentVersion`  
- 保存并关闭 → 一个 MANUAL 次版本  
- **本期不要求填写变更原因（F4）**

## 4. 「查看历史」可见性（数据权限）

### 4.1 角色分层（F1 + F2）

| 角色层级（示例） | 可见历史范围 |
|------------------|--------------|
| **业务人员**（编制/检测/业务员等） | 仅 **当前最新 major** 下：`V{n}.0` + 全部次版本 `V{n}.1…` |
| **高级角色**（质量负责人等，可配） | 上表 **+** 旧主版本整链（`V1.0/V1.1…`、`V2.0…` 等），即「高级历史」 |
| 无 `doc:{type}:history` | 不显示「查看历史」按钮 |

权限建议拆分：

```
doc:{docType}:history              # 查看当前 major 历史
doc:{docType}:history_advanced     # 查看跨 major 旧主版本（质量负责人等）
doc:{docType}:rollback             # 同 major 次版本回滚
doc:report:edit_after_issue_config # 配置「签发后是否可编辑」（实务版下才露出）
lab:run_mode:switch                # 切换合规版/实务版
```

### 4.2 历史弹窗能力（与运行模式叠加，见 §10）

| 版本 | 在线查看 | 下载 | 编辑 |
|------|----------|------|------|
| current | ✅ | ✅（有下载权） | ✅（阶段+模式允许） |
| 可见的历史版 | ✅ | ❌ | ❌ |

弹窗列：版本号、来源（系统/人工/回滚/流程回退）、操作人、时间、回滚自、触发节点。

## 10. 合规版 / 实务版一键切换（方案设计）

### 10.1 问题

17025 严格要求例如：**报告签发后不允许在线改文件**，除非走退回。客户现场有时需要签发后仍可改。需要：

- 日常可按客户实际放开部分「不合规」能力  
- 迎检一键切回合规表现，避免检查时露出不合规配置与次版本痕迹  

### 10.2 核心概念

| 模式 | 代号 | 定位 |
|------|------|------|
| **合规版** | `compliance` | 迎检 / 内审默认；强制执行标准底线 |
| **实务版** | `practical` | 客户实际作业；允许配置并启用白名单内的弹性项 |

**一键切换**：实验室级（或租户级）总开关；切换本身需 `lab:run_mode:switch`，并写审计（谁、何时、从哪到哪、原因）。

### 10.3 生效模型（推荐：显示层 + 强制覆盖层）

```
最终行为 = ComplianceGuard( mode, PracticalFlexibilityConfig )
```

- **实务版**：读取并应用 `PracticalFlexibilityConfig`；相关配置入口**显示**（仍受「谁能配置」权限控制）  
- **合规版**：
  - 相关配置入口**隐藏**  
  - 运行时**忽略**实务配置值，强制走合规规则  
  - **不删**实务配置数据（切回实务版后恢复原设置）  

这样迎检不用改配置、也不丢客户设定。

### 10.4 已纳入的两处差异（本期先记这两处，后续继续补）

#### （1）报告签发后是否允许在线编辑

| | 实务版 | 合规版 |
|--|--------|--------|
| 配置入口「签发后允许编辑」 | **显示**；仅持有 `doc:report:edit_after_issue_config` 者可改 | **隐藏** |
| 运行时 | 若配置=允许 → 签发后仍可 PageOffice（出次版本）；若=不允许 → 同合规 | **强制不允许**在线编辑 |
| 例外 | — | 仅通过**流程退回**解除签发态后，方可再编辑（退回本身可触发文件 major 变动，见 §3.2） |

> 标准立场：签发后改报告不符合 17025；合规版必须锁死。实务版把风险交给实验室管理层配置与审计。

#### （2）「查看历史」弹窗展示范围（在 F1 角色过滤之上再叠加）

| | 实务版 | 合规版 |
|--|--------|--------|
| 业务人员 | 当前 major：`V{n}.0` + 次版本 | 当前 major：**仅系统主版本 `V{n}.0`**（次版本不在页面展示） |
| 质量负责人等（advanced） | 跨 major 全链（主+次） | 跨 major：**仅各系统主版本 `V*.0`**（所有次版本不在页面展示） |

说明：

- 合规版隐藏次版本是**页面展示策略**，降低检查时「报告/记录曾被手工改过多版」的观感干扰；底层是否仍存库见数据策略（建议仍存，仅 UI/API 对常规查询过滤；内审导出另议，后续补充）  
- 与 F1 不冲突：先按模式滤「主/次」，再按角色滤「当前 major / 全 major」

### 10.6 切换审计

每次切换记录：`fromMode`、`toMode`、`operator`、`time`、`reason`、切换瞬间生效的弹性配置快照（可选）。  
检查时可证明：检查日处于合规版，且弹性入口不可用。

### 10.7 扩展机制（便于后续补充）

所有「合规冲突项」登记进弹性注册表，避免逻辑散落：

```ts
interface FlexibilityFlag {
  key: 'allowReportEditAfterIssue' | string; // 后续追加
  title: string;
  complianceForcedValue: unknown;  // 合规版强制值，如 false
  configPermission: string;        // 谁能在实务版改这项
  affects: ('edit_gate' | 'history_ui' | ...)[];
}
```

**已登记**：`allowReportEditAfterIssue`、`historyHideManualMinorsInCompliance`（合规版历史只展示主版本）。  
**待讨论再补**：其它文件签发/审核锁定、原始记录审核后编辑、客户可见性等（你后续想到再往注册表加）。

### 10.8 非目标（本骨架不做）

- 按委托单逐单切换模式（默认实验室级；若要委托级覆盖，后续单开）  
- 自动根据「是否迎检日历」切换  
- 合规版下物理删除次版本文件

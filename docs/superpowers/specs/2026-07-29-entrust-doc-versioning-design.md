# 委托详情页 · 文件版本管理设计（ISO/IEC 17025 平衡方案）

**日期**: 2026-07-29  
**范围**: 委托详情页内全部业务文件的版本生命周期（生成 / 系统更新 / 人工编辑 / 查阅 / 审计）  
**状态**: 设计草案（待确认开放问题）  
**依据**: ISO/IEC 17025:2017（GB/T 27025-2019）§7.5 技术记录、§7.8 报告结果、§7.11 数据控制、§8.4 记录控制

---

## 1. 背景与目标

委托详情页集中展示一份委托下的各类业务文件。用户可对文件**手动编辑保存**，业务流程推进也会**系统回填/重生成**文件内容——二者都会产生新版本。

**目标**（在 17025 与可用性之间取平衡）：

1. **放开编辑入口**：各文件操作列提供「编辑」，但受严格权限与流程闸门控制  
2. **全量留痕**：谁、何时、因何、改了什么、新旧文件均可追溯  
3. **区分更新来源**：`SYSTEM`（流程驱动） vs `MANUAL`（人工编辑）  
4. **不可篡改历史**：历史版本只读；当前生效版明确；已签发/已发放文件禁止静默覆盖  
5. **与现有「变更记录」解耦又关联**：委托字段变更走变更审批；文件版本走文件版本链；必要时交叉引用

### 2.3 模版侧已配置的 6 类单据（对照）

`检测委托书 / 收费通知单 / 检测任务单 / 检测任务及流转单 / 还样退库确认表 / 退样申请表`

后两类当前未在委托详情页独立成块（可能嵌在流转/退样流程），版本模型仍按「单据实例」统一，不按页面区块碎片化。

## 3. 核心概念

| 术语 | 定义 |
|------|------|
| **文件实例 (DocumentInstance)** | 某委托下某一 `docType` 的一份逻辑文件（可含 Word/PDF 双格式） |
| **版本 (DocumentVersion)** | 实例下不可变快照；版本号单调递增 `v1, v2, …` |
| **当前生效版 (current)** | 对外展示、下载默认指向的版本；通常为最新已确认版 |
| **更新来源 (source)** | `SYSTEM` \| `MANUAL` \| `IMPORT` |
| **版本状态 (status)** | `draft` → `confirmed` → `issued` / `superseded` / `void` |
| **内容指纹 (contentHash)** | 文件字节或规范化 DOM 哈希，防静默篡改（对齐 7.11） |

```
DocumentInstance (entrustId + docType [+ specimenId?])
  └─ DocumentVersion[]  (immutable blobs + metadata)
        ├─ v1 SYSTEM  confirmed
        ├─ v2 MANUAL  confirmed   ← current
        └─ v3 SYSTEM  draft       （流程触发的待确认草稿，可选策略）
```

## 4. 版本触发规则

### 4.1 系统更新（SYSTEM）

| 触发场景 | 影响文件 | 建议行为 |
|----------|----------|----------|
| 委托登记完成 / 确认 | 委托单、任务单、收费通知单… | 首次生成 v1 |
| 委托信息变更审批通过 | 依赖字段的已生成单据 | **新版本**（禁止原地改历史版） |
| 收样 / 制备 / 发样 / 接收 / 还样 / 退样 | 流转单 | **追加节点行 → 新版本**（或「追加修订」语义，见开放问题 Q3） |
| 报告编制导出 | 报告 Word/PDF | 新版本；签发后锁定 |
| 报告发放 / 邮寄 | 发放记录、邮寄单 | 新版本或附属记录 |
| 模版切换 / 重生成 | 对应单据 | 新版本；需权限 + 原因 |

### 4.2 手动更新（MANUAL）

1. 操作列「编辑」→ 鉴权通过 → 打开在线编辑器或下载-改-回传  
2. 保存前强制填写 **变更原因**（必填）  
3. 系统生成下一版本号，`source=MANUAL`，记录操作人、时间、diff 摘要  
4. 原版本状态改为 `superseded`；新版成为 `current`（若策略为「保存即生效」）  
5. 写入审计日志 + 可选通知质量负责人

### 4.3 冲突与优先级

当「人工改过的文件」再次被系统流程更新时（开放问题 **Q1**），候选策略：

| 策略 | 说明 | 适用 |
|------|------|------|
| **A. 系统始终出新版** | 保留人工版为历史；系统版成为 current；UI 提示「已覆盖人工修订」 | 流转单节点回填 |
| **B. 人工锁** | 人工编辑后打 `manualLock`；系统更新变 draft，需人工合并确认 | 委托单、收费单 |
| **C. 字段级合并** | 结构化字段系统可写，自由文本区保留人工 | 实现成本高 |

**草案推荐**：流转单/原始记录偏 **A**；委托单/收费通知单偏 **B**；报告签发后一律禁止系统静默覆盖（只能废止重出）。

## 5. 与 17025 的映射（平衡设计）

| 标准要求 | 设计落点 |
|----------|----------|
| 7.5 技术记录当时当地、可复现 | 版本时间戳、操作人、内容指纹；原始记录禁止无痕改 |
| 7.5 修改留痕 | 永不物理删除历史版；diff / 并排对比 |
| 7.8 报告准确清晰 | 报告 `issued` 后只读；更正走「修订报告 / 作废重发」流程 |
| 7.11 防篡改、权限 | RBAC + 服务端鉴权；存储只追加；哈希校验 |
| 4.2 保密性 | 下载/预览权限与委托数据权限一致 |
| 8.4 记录控制 | 保留期限、归档策略按文控程序配置 |
| 6.2 人员能力 | 「编辑」权限绑定岗位授权，非仅角色勾选 |

### 平衡原则（对「一般不允许在详情页改文件」）

- **默认只读**：无权限用户仅见下载/预览/版本历史  
- **编辑是特权操作**：独立权限码 `doc:{type}:edit`，可按阶段关闭  
- **高风险文件二次确认**：原始记录、已签发报告 → 编辑需「双人复核」或质量负责人审批（开放问题 **Q2**）  
- **原因强制**：无原因不可保存  
- **界面提示**：编辑入口旁显示 17025 提示文案（可配置开关）

## 6. 权限模型

```
doc:{docType}:view
doc:{docType}:download
doc:{docType}:edit          # 操作列「编辑」
doc:{docType}:regen         # 手动触发系统重生成
doc:{docType}:void          # 作废某版本
doc:version:compare
doc:report:issue            # 报告签发（进入 issued）
doc:record:amend            # 原始记录修订（最高敏）
```

| 文件 | 建议默认可编辑角色 | 阶段闸门（示例） |
|------|--------------------|------------------|
| 委托单 | 业务员、文控 | 报告签发后只读，或仅质量负责人 |
| 任务单 | 调度、技术负责人 | 检测开始后只读 |
| 流转单 | 默认禁手动编辑；仅系统回填 | 例外：文控纠错 + 原因 |
| 收费通知单 | 商务、财务 | 已开票后锁定金额区 |
| 报告 | 编制员 | `issued` 后禁止；走修订流程 |
| 原始记录 | 检测员本人 / 授权复核 | 审核通过后禁改或仅 amend 流程 |
| 邮寄单 | 发放岗 | — |

操作列示意：

```
[预览] [下载] [编辑] [版本]     ← 按权限显隐
                 └ 版本抽屉：vN 列表 / 来源标签 / 对比 / 回滚申请
```

## 7. 数据模型（草案）

```ts
type DocType =
  | 'entrust_form'      // 检测委托书
  | 'task_sheet'        // 检测任务单
  | 'flow_sheet'        // 检测任务及流转单
  | 'fee_notice'        // 收费通知单
  | 'report'            // 检测报告
  | 'mail_sheet'        // 邮寄单
  | 'return_confirm'    // 还样退库确认表
  | 'return_apply'      // 退样申请表
  | 'original_record'   // 原始记录
  | 'pre_notice';       // 预通知书（若保留）

interface DocumentInstance {
  id: string;
  entrustId: string;
  docType: DocType;
  specimenId?: string;       // 按试样拆分时
  currentVersionId: string;
  manualLock: boolean;
  createdAt: string;
}

interface DocumentVersion {
  id: string;
  instanceId: string;
  versionNo: number;         // 1..n
  source: 'SYSTEM' | 'MANUAL' | 'IMPORT';
  status: 'draft' | 'confirmed' | 'issued' | 'superseded' | 'void';
  reason: string;            // 变更原因（SYSTEM 可填触发事件码）
  triggerEvent?: string;     // e.g. SAMPLE_RECEIVE, ENTRUST_CHANGE_APPROVED
  operatorId: string;
  operatorName: string;
  createdAt: string;
  contentHash: string;
  files: { format: 'docx' | 'pdf' | 'html'; url: string; name: string }[];
  parentVersionId?: string;  // 基于哪一版编辑/派生
  changeSummary?: string;    // 自动或人工摘要
  relatedChangeRecordId?: string; // 关联委托变更单
}
```

**存储原则**：对象存储只追加；DB 元数据可改状态，不可改 `contentHash` / 文件 URL。

## 8. UI 方案（委托详情）

### 8.1 列表行增强

| 列 | 说明 |
|----|------|
| 文件名 | 链到当前生效版预览 |
| 当前版本 | `v3` + 来源徽标（系统/人工） |
| 生成/更新时间 | 当前版时间 |
| 操作 | 预览 · 下载 · **编辑** · **版本** |

### 8.2 版本抽屉 / 弹窗

- 时间倒序列表：版本号、来源、操作人、原因、状态  
- 操作：预览、下载、与当前对比、（授权下）设为生效 / 发起回滚申请  
- 禁止：物理删除；无权限隐藏编辑相关按钮

### 8.3 编辑流

```
点击编辑 → 权限+阶段校验 → 告知「将生成新版本」
  → 编辑器 / 上传替换件
  → 填写原因（必填）→ 可选勾选「锁定，禁止系统覆盖」
  → 保存 → v(n+1) MANUAL confirmed → 审计日志
```

### 8.4 系统更新提示

流程回填产生新版时，若上一版为 MANUAL，Toast/站内信：「流转单已由系统更新为 v4（基于收样事件），原人工版 v3 已归档可对比」。

## 9. 与「变更记录」模块关系

| | 变更记录（现有） | 文件版本（本设计） |
|--|------------------|-------------------|
| 对象 | 委托/样品**字段** | **文件内容**快照 |
| 流程 | 申请 → 审批 | 编辑/系统事件 → 新版本（报告修订可另挂审批） |
| 关联 | 审批通过可触发相关文件 SYSTEM 新版本，写入 `relatedChangeRecordId` |

## 10. 非目标（本阶段不做）

- 模版库自身的多版本管理（已有单据/报告模版版本能力）  
- 跨委托的文件合并版本树  
- 客户门户侧的版本差异可视化（可二期）

## 11. 推荐落地节奏

1. **P0**：统一 `DocumentInstance/Version` 模型；列表展示当前版本+来源；版本历史只读  
2. **P0**：操作列编辑入口 + 权限 + 原因强制（先覆盖委托单/任务单/收费单）  
3. **P1**：流转单 SYSTEM 追加版本策略；报告签发锁定  
4. **P1**：原始记录 amend 流程；版本对比  
5. **P2**：人工锁与系统更新冲突策略产品化；双人复核

## 12. 开放问题（请确认）

以下问题会影响数据模型与交互，请逐条拍板：

### Q1. 人工编辑后，系统流程再次更新同一文件时，默认策略？
- A. 系统直接出新版并成为 current（人工版归档）  
- B. 人工锁：系统只产 draft，需人工确认合并  
- C. 按文件类型分别配置（草案倾向此项）

### Q2. 原始记录、已签发报告的「编辑」是否必须审批/双人复核？
- A. 必须（更贴 17025）  
- B. 仅权限码控制，留痕即可  
- C. 可配置：实验室在体系参数中开关

### Q3. 流转单节点回填：每个节点一个新版本，还是「同一版本内追加行 + 行级审计」？
- A. 每节点新版本（审计简单、存储多）  
- B. 行级追加审计 + 定期打版本快照（更贴近纸质流转）  
- C. 仅在关键节点（收样完成/全部还样/退样完成）打版本

### Q4. 产品检测预通知书是否仍作为可版本管理的文件？
- A. 详情页移除，与模版侧下线一致  
- B. 保留为只读派生视图，不提供编辑/版本  
- C. 纳入版本管理，与委托单同等

### Q5. 版本号展示规则？
- A. 简单递增 `v1, v2, …`  
- B. 语义化：`v1.0` 系统主版 / `v1.1` 人工修订  
- C. 报告单独用 `Rev.0 / Rev.1`（对齐报告更正习惯），其他用 vN

### Q6. 「编辑」实现方式？
- A. 仅支持下载 Word → 本地改 → 回传上传（替换为新版）  
- B. 在线 OnlyOffice/类似协同编辑  
- C. 先 A 后 B

### Q7. 历史版本是否允许「回滚为当前」？
- A. 允许（实为基于旧版再生成一版，不删中间历史）  
- B. 禁止回滚，只能查看/对比  
- C. 回滚需审批

### Q8. 报告 PDF 与 Word 是否共用同一 versionNo？
- A. 同一版本下挂多格式文件（推荐）  
- B. Word/PDF 分两条版本链

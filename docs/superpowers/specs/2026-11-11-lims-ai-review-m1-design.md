## 1. 意图与为什么（Intent）

在 LIMS 现有「报告编制 → 报告审核 → 报告验证 / 签发 → 合格证」链路里，报告审核目前靠人工逐项核对，耗时且易漏。第一期要在**小范围内跑通一条完整的 AI 审查闭环**：报告流转到审核环节时自动触发 AI 审查，产出「问题清单 ＋ 通过 / 不通过结论」交给人工审核员逐条确认处置。

第一期是一个**薄的纵向切片**，目标不是覆盖全部规则，而是：
1. 验证整条闭环（触发 → 取数 → 判定 → 汇总 → 展示 → 人工处置 → 沉淀）在真实链路里走得通；
2. **预留可扩展结构**（通用集 / 品类专属绑定、ML / LLM 引擎位、历史案例库），让后续迭代扩规则、扩品类、接入模型时不需要大改地基。

所以第一期的成功定义是"闭环成立 + 结构可扩"，而不是"规则齐全 / 命中率高"。

## 2. 目标 / 非目标 / 反目标

### 2.1 目标（Goals）
- 从规则台账「通用」池中挑选 **8 条确定性强、误报极低、不依赖品类专属限值、所有品类在审核阶段都要核**的规则，横跨 A / B / C 三维度，落地可运行的规则引擎。
- 打通闭环：报告流转到「报告审核」**自动触发** AI 审查 → 输出问题清单 ＋ 通过 / 不通过结论。
- 两个结果入口：① 独立「审核工作台」统览全系统 AI 审查结果；② 现有 LIMS 报告审核页**内嵌 AI 审查结果卡片**。
- 审核员可逐条确认 / 处置，并可**人工覆盖** AI 结论（须填理由、留痕）。
- 每个审核案例（报告快照 ＋ AI 结论 ＋ 人工处置 ＋ 误报 / 漏报标注）**沉淀到历史案例库**，为后续 ML / LLM 积累数据。
- 数据层与知识库层**预留扩展结构**：通用 / 品类绑定表、`is_universal` / `param_schema` 字段、ML / LLM 引擎位、历史案例库。

### 2.2 非目标（Non-Goals，第一期不做）
- 不做 ML 模型层（M4）与 LLM 引擎层（M5）的任何推理逻辑（架构里只预留位置）。
- 不配置任何品类专属规则与品类绑定（绑定表建好但空跑）。
- 不扩规则到全量 45 条，不追求覆盖率 / 命中率指标达标。
- AI 结论**不自动改写报告状态**、不自动签发 / 退回；闭环终点为"审核员看到结论并处置"，不强制走到出合格证。
- 历史案例库 M1 **只写不消费**（不做任何模型训练 / 在线分析）。
- **不改动现有「判定规则 / 报告判定」子系统**（样品合格性 ABC 质量特性分级），见 §4.4。

### 2.3 反目标（Anti-Goals，出现即视为失败）
- AI 成为签发责任主体，或在无人工确认下直接影响报告状态 / 签发。
- 规则引入品类专属数值（如 8 套、6 个月），使"通用规则"产生品类相关误报。
- 预留结构被省掉或写死，导致二期扩品类 / 接模型必须推翻地基重做。
- 规则对非抽样类报告（型式 / 出厂 / 例行 / 委托送检）产生系统性误报。

## 3. 约束（Constraints）
- 责任边界：AI 只输出预审意见与问题清单，最终签发由授权签字人确认。
- 取数只读：**"只读"指不回写 LIMS 业务数据**（AI 只写自己的 `ai_review_*` 表）。它**不**限制 LIMS 主动通知 AI、也不限制 AI 读取 LIMS 的只读状态 —— 触发机制见 §6.1。
- 判定确定性：第一期规则必须是确定性规则，误报目标 < 1%；不引入概率 / 生成式判定。
- LIMS 字段现状未核：所有依赖的 LIMS 字段均标「待 Week 1 调研确认」，字段命名以 LIMS 实际为准。
- 规则可信度：8 条规则的判定式由台账描述推导，状态默认「待审核员确认」，Week 1 由领域顾问校准。

## 4. 方案选型（Approaches）

### 4.1 架构形态
以飞书「LIMS-AI Review 系统架构总览」（图二）为骨架，而非仅用「M1 技术架构」（图一）。考虑过三种：

- **A · 仅按图一最小技术架构**（审核工作台 + FastAPI + RuleEngine + Adapter + 4 张表）。最省，但缺少显式的知识库层与案例沉淀位，二期接 ML / LLM、扩标准库时要补地基。
- **B · 直接上图二全量**（含 ML / LLM / 历史案例 / 行业术语）。结构最完整，但 M1 要做的推理层用不上，超出"最小闭环"。
- **C · 图二骨架 + M1 裁剪（选定）**：保留用户交互层、API 编排层、审核编排器、AI 引擎层（仅规则引擎）、**数据集成层、知识库层（含历史案例库）**；ML / LLM 引擎层**占位预留**。

**选定 C**，理由：既满足"最小闭环"，又把"取数 / 取判定依据 / 数据沉淀"的底座一次搭对，二期只填充不改骨架。用户明确倾向保留数据集成层与知识库层作为取值与取判定依据的基础，并要求把历史案例库纳入 M1 以沉淀数据供后续 ML / LLM 使用。

### 4.2 部署形态（本设计的决定，可推翻）
采用图一推荐的**方案 A · 独立微服务（Python FastAPI）**：独立部署、只读接口取数、不侵入 LIMS 主系统。理由：低风险、技术栈灵活、与现有系统解耦，便于灰度与回滚。（备选方案 B「LIMS 内部模块」数据访问最直接但与 LIMS 技术栈强耦合，暂不采用。）

### 4.3 结论聚合（本设计的决定，可推翻）
按规则严重度聚合为单一总结论：
- 命中任一「严重」规则 → **不通过（建议退回）**；
- 无严重、命中「一般」 → **通过待确认（有问题需处置）**；
- 仅「轻微 / 提示」或全通过 → **通过（含提示项）**。

审核员可**人工覆盖** AI 总结论与逐条结论，覆盖必须填写处置理由并写入 `ai_review_feedback`（留痕）。

### 4.4 与现有判定子系统的关系（本设计的决定）
现有 `judgment-rules.html` / `report-judgment.html` 是一套**样品合格性判定**系统：按「样品分类 × 试验类型」套用判定方案，用 ABC **质量特性分级**（A / B / C 类不合格）得出样品**合格 / 不合格**。

本功能的「ABC」是**完全不同的轴**：A 数据完整性 / B 逻辑一致性 / C 格式规范性，判的是**报告本身是否可签发**，不是样品合格与否。因此 **AI 审查是独立子系统**：
- 不复用、不改动现有判定方案 / 条件引擎，二者只是字母相同；
- 规则配置为**独立的新界面**（审核规则库），独立菜单区，不嵌入现有判定规则页；
- 数据上两套互不写入。

### 4.5 构建载体（开放决策 —— 待拍板）
本文描述的是**目标系统**（独立 FastAPI 微服务 + PostgreSQL）。但本仓是静态原型仓（HTML/JS + localStorage mock，push 到 Vercel）。第一期究竟是：
- **(甲) 在本原型仓里先把闭环原型出来**（仿 `tests/twin` 模式：新增审核工作台页 + 报告审核页卡片 + 用 JS / localStorage 模拟 7 张表与规则引擎 + Playwright 回归），还是
- **(乙) 直接起真实后端服务**（新仓 / 新服务：DDL + ORM + 调度 + API 契约 + 后端测试），

是**最影响实现计划的一个岔路**，交由产品负责人拍板（见文末「待确认」）。本设计的架构 / 数据模型 / 规则口径对两种载体都成立，仅实现技术栈与测试方式不同。

## 5. M1 架构层（决定项）

自上而下（详见 Canvas）：
1. **用户交互层 Frontend**：审核工作台（统览全系统 AI 审查结果）、问题看板、统计仪表盘、规则配置；另：现有 LIMS 报告审核页内嵌「AI 审查结果卡片」。
2. **API 网关 ＆ 服务编排层**：统一接入、鉴权、跨服务调度。
3. **审核编排器 Orchestrator**：协调引擎、汇总审核结果、生成审查报告（问题清单 ＋ 通过 / 不通过结论）。
4. **AI 审核引擎层 Core**：规则引擎 RuleEngine（M1 落地，8 条通用规则）；ML 模型层（M4 预留）、LLM 引擎层（M5 预留）。
5. **数据集成层 Integration（保留）**：LIMS 数据接口（报告 / 委托 / 原始记录）、设备数据接口（校准有效期等）、文档管理 —— Step1 取数。
6. **知识库层 Knowledge（保留）**：审核规则库（规则台账 ＋ 通用 / 品类绑定结构预留）、检测标准知识库（标准限值 / 标准号，M1 取判定依据）、**历史案例库（M1 落地，只沉淀不消费）**、行业术语库（预留）。
7. **数据层**：PostgreSQL 新增表（见 §7）＋ LIMS 数据库只读接入。

## 6. 闭环与交互（决定项）

### 6.1 触发与流程
> **触发机制**：优先由 LIMS 在"流转到报告审核"时**事件回调 / 通知** AI 服务的接口（AI 不回写业务数据，仍可被调用）；若目标 LIMS 无事件能力，退化为 AI 服务**轮询只读状态字段**（轮询间隔与可接受延迟 SLA 于 Week 1 定）。原型载体（§4.5 甲）下用页面状态变更模拟该触发。

1. 报告编制完成，流程流转到「报告审核」状态 → **自动触发** AI 审查（无需人工点按）。
2. 编排器调用规则引擎；引擎从数据集成层取数、从知识库层取判定依据。
3. 规则引擎逐条判定 8 条规则，产出每条命中结果（通过 / 命中 + 严重度 + 证据字段）。
4. 编排器汇总为「问题清单 ＋ 通过 / 不通过结论」，写入 `ai_review_results` / `ai_review_issues`。
5. 结果呈现在**审核工作台**与**报告审核页卡片**两处。
6. 审核员逐条确认 / 处置（接受 / 覆盖 + 理由）→ **闭环终点**。
7. 处置完成后，该案例（报告快照 ＋ AI 结论 ＋ 逐条处置 ＋ 误报 / 漏报标注）沉淀至 `ai_review_cases`。

### 6.2 两个入口的分工
- **审核工作台**（新页面）：管理员 / 审核员统览全系统 AI 审查结果，按状态 / 严重度 / 规则筛选，进入单份处置。
- **报告审核页卡片**（嵌入现有 LIMS 页面）：审核员在原有审核动作里，先看到 AI 审查结果再逐条处置，不改变原审核页主流程，仅增补一张结果卡片。

## 8. 第一期规则清单（决定项，8 条全留）

全部取自台账「通用」池，确定性、不含品类专属数值，跨检测业务类型与行业成立：

| 规则ID | 维度 | 判据（口径） | 严重度 | 主要字段 |
| --- | --- | --- | --- | --- |
| A01-1 | A 数据完整性 | 样品编号必填且符合编号规则 | 严重 | 样品编号 |
| A01-6 | A 数据完整性 | 检测标准号必须带年号 | 严重 | 标准号年号 |
| A02-1 | A 数据完整性 | 委托检测项目都有对应实测结果 | 严重 | 委托项 / 实测值 |
| B01-1 | B 逻辑一致性 | 关键日期先后（见 §8.1 修订口径） | 严重 | 收样 / 检测 / 报告 / 抽样日期 |
| B01-2 | B 逻辑一致性 | 设备校准有效期覆盖检测日期 | 严重 | 设备校准有效期 |
| B03-1 | B 逻辑一致性 | 报告引用标准号 == 实际检测标准 | 一般 | 标准号年号 |
| C02-5 | C 格式规范性 | 检测 / 审核 / 批准签名位齐全 | 严重 | 签名位 |
| C01-4 | C 格式规范性 | 计量单位与参数匹配 | 一般 | 实测值 / 单位 |

### 8.1 B01-1「关键日期先后」修订（重点）

**原判定式**：`sampling_date <= receive_date <= test_date <= report_date`，且强制依赖抽样日期。

**问题（经确认成立）**：
1. **抽样日期并非所有报告都有**。只有"抽样检验 / 监督抽查 / 委托抽样"等由实验室或监督方执行抽样的业务，才有实验室口径的抽样日期；大量"委托送检（送样）"由客户直接送样，实验室无抽样环节，抽样日期可能缺失或为客户自填。
2. **检测业务类型多样**：型式试验、出厂（例行）试验、抽样检验、委托检验等，日期链各不相同；型式 / 出厂 / 例行试验通常没有"抽样"节点。
3. **跨行业普适性**：型式 / 出厂（例行）/ 抽样 / 委托是合格评定**通用的检验类别**，机械、电工电子、化工 / 化学检测同样区分（化学领域命名可能略有差异，如"例行分析 / 型式分析"），不能假定每份报告都有抽样节点。

**结论**：日期先后逻辑本身仍是一条优质通用确定性规则，问题只在"强制抽样日期"和"假定四段都存在"。修订为**只校验实际存在的日期之间的先后顺序**：

- 恒定核心链（每份报告都有）：`收样 / 受理日期 ≤ 检测（完成）日期 ≤ 报告签发日期`。
- 抽样日期做**条件分支**：`若存在抽样日期，则 抽样日期 ≤ 收样 / 受理日期`；**抽样日期缺失不判违规**。

修订后判定式（伪代码）：

```
(!exists(sampling_date) || sampling_date <= receive_date)
&& receive_date <= test_date
&& test_date <= report_date
```

**附注**：
- 字段命名（收样 vs 受理）以 LIMS 实际为准，Week 1 字段调研确认。
- "某些业务类型必须有抽样日期 / 抽样单"这类完整性要求，后续作为**按检测业务类型**（非按品类）的专项规则补充，与通用集解耦。检测业务类型是通用业务属性，不算品类绑定。
- 其余 7 条规则已逐一核查，不含同类"假定抽样"的隐含依赖；B01-1 是唯一需修订项。

## 9. 预留扩展结构（决定项）

M1 建好、但不启用的扩展位，确保二期免大改：
- **通用 / 品类绑定**：`is_universal` / `param_schema` 字段 + `ai_review_categories` + `ai_review_category_bindings` 两表（空跑）；未配置品类走通用集 + `CAT-UNCAT-01`。
- **ML / LLM 引擎位**：架构层保留 ML 模型层（M4）、LLM 引擎层（M5）接口位，不实现推理。
- **历史案例库**：`ai_review_cases` 持续沉淀，作为 M4 / M5 的训练与评估数据来源。
- **行业术语库**：知识库层预留，后续分期。

## 10. 验收标准（M1）
- 报告流转到「报告审核」能**自动触发** AI 审查并产出问题清单 ＋ 通过 / 不通过结论。
- 审核工作台可统览并筛选全系统审查结果；报告审核页可见 AI 结果卡片。
- 审核员可逐条处置并人工覆盖结论，覆盖理由写入 `ai_review_feedback`。
- 每个完结案例写入 `ai_review_cases`（含误报 / 漏报标注）。
- 8 条规则全部可运行；B01-1 按 §8.1 修订口径实现，对型式 / 出厂 / 例行 / 委托 / 抽样类报告均不产生误报。

- 7 张表建成，其中品类两表空跑、`ai_review_cases` 只写；未配置品类路径输出 `CAT-UNCAT-01`。
- 规则判定式全部确定性，无品类专属数值；规则状态默认「待审核员确认」。
